<interfaces>
- Search route is exact `GET /public/search`; its query authority is `publicSearchQuerySchema`. It returns empty-query directly without invoking `searchPage` and otherwise parses the repository output through `publicSearchResponseSchema`.
- Search 400 bodies distinguish only `invalid_search_query` and `invalid_search_page`; timeout is exactly HTTP 503 `{ error: "search_unavailable" }`. A narrowly scoped discovery-route catch maps every other search or related repository exception to HTTP 500 with bytes exactly `{"error":"discovery_error"}` parsed by `publicDiscoveryInternalErrorResponseSchema`; it does not rely on or change Fastify's global/default error handling.
- Related route is exact `GET /public/articles/:slug/related`, takes no visitor limit, and returns `publicRelatedPostsResponseSchema` with at most `publicRelatedPostLimit = 4` items.
- `relatedBySlug(slug)` runs one repeatable-read/read-only transaction: source selects internal `id/categoryId` under `publicPredicate`; candidates apply `publicPredicate`, exclude source ID, require category/tag overlap, compute internal categoryMatch and sharedTagCount, order lexicographically, limit four, then hydrate strict cards.
- Related ordering is `categoryMatch DESC, sharedTagCount DESC, publishedAt DESC, id DESC`; it is not an additive magic score and neither score component crosses the repository return boundary.
- Source absent under `publicPredicate` returns null and route reuses `publicPostNotFoundResponseSchema`. A public source with no overlap returns `{ items: [] }`.
- Search/related routes remain internal API paths reached by future browsers through existing relative `/api` proxy; no Web or server-address code is added in Phase 6.
</interfaces>
