# Phase 5 Implementation Patterns

This is a repository-only planning map for the three ordered Phase 5 plans. It records the closest working analogs and the ownership boundaries that must survive the gap closure. It is not authorization to contact a host, install a unit, create a production destination, or turn a synthetic result into production evidence.

## Invariants shared by all three plans

- The browser owns only relative `/api` and `/media` traffic. `apps/web/next.config.ts` is the existing reverse-proxy seam; `INTERNAL_API_ORIGIN` remains a server-side rewrite input, never client code. `scripts/check-boundaries.mjs` already detects Web database/filesystem/media ownership, direct public API origins, outbound browser fetches, node addresses, and API/PostgreSQL public planes.
- API content/storage remains authoritative. `apps/api/src/content/media-service.ts` creates UUID-addressed `/media/<uuid>` records, `apps/api/src/routes/media.ts` serves API-owned derivatives, and `apps/api/src/content/public-repository.ts` projects only `coverMediaId` as a public cover. The Web `ArticleBody` deliberately trusts server-sanitized HTML; it must not become a second sanitizer.
- The current backup rehearsal is intentionally narrow. `scripts/backup/paths.mjs`, `policy.mjs`, `create.mjs`, `manifest.mjs`, and `restore.mjs` accept only generated temporary roots plus `blogxverify_*`/`blogxrestore_*` authority. Those predicates must not acquire a production exception or a mode flag.
- The canonical release artifact stays tracked, locator-free, and `BLOCKED`: `ops/release-evidence.blocked.json` plus `scripts/release-gate.mjs --expect-blocked`. Generated `/tmp/blog-x-release-evidence-*` bundles are test-only evidence inputs. A passing fake bundle, local verifier, Git state, or elapsed time never changes the canonical state.
- Reuse the project’s strict-object/version/schema/hash/test conventions: explicit key lists, `lstat` no-link checks, exact generated root predicates, SHA-256 binding, injected dependencies for side effects, and TAP/Playwright semantic checks which fail on skip/TODO/zero tests. Closest examples are `scripts/release-gate/{schema,bundle,validate}.mjs`, `scripts/backup/{manifest,restore}.mjs`, and `scripts/local-verify.mjs`.
- No Phase 5 file may add SSH/SCP/rsync/sftp/curl/wget deployment behavior, remote execution, arbitrary shell command hooks, automatic unfreeze/deploy/rollback, direct browser data-plane access, public import/restore APIs, remote image retrieval, cloud credentials, server addresses, or live claims. Extend `check-boundaries.mjs` and its fixture tests whenever a new operational surface could accidentally make one of those claims.

## 05-01 — published image authority and legacy disposition

### Required data flow and authority split

```text
editor upload -> MediaPanel -> /api/admin/media -> API media record -> /media/<uuid>
                                       |                         |
                                       +-> Markdown / coverMedia +-> public detail -> Web image request

legacy markdown / cover_url -> classify without rewriting source -> review marker -> save/publish decision
                                                \-> public renderer removes non-media img src
ordinary Markdown href --------------------------> existing http/https anchor sanitization
```

`apps/api/src/content/markdown.ts` is the closest renderer analog. It already walks the HAST before `rehype-sanitize` and deletes an image `src` when `allowedImageSource()` says no. Replace its currently mixed policy (exact `/media/<uuid>` **or** absolute HTTP(S), plus sanitizer `src: ["http", "https"]`) with a shared exact authority function. The function must accept only the literal root-relative UUID form, with no host, query, fragment, encoded alternative, traversal, malformed UUID, or relative non-media path. Keep `href: ["http", "https"]` and renderer-generated `#heading` anchors distinct; do not derive image policy from link policy.

Classification of retained source must use parsed Markdown image nodes, not a raw-source regex. Reuse the `unified().use(remarkParse).use(remarkGfm)` AST path already used by `renderMarkdown()`, but place classification in the new policy/migration layer so render output, persistence, and migration share the same exact decision. Code fences, escaped text, ordinary hyperlinks, and raw disabled HTML must not produce a false legacy finding.

`apps/api/src/content/article-service.ts` has the correct transactional enforcement seam: it validates before `repository.update()` and re-validates retained data when the lifecycle action is `publish`. `admin-posts.ts` is the API/UI DTO authority, and `admin-repository.ts` is the locked-row persistence/hydration seam. Do not put publication eligibility solely in the React editor or solely in public rendering: direct API writes and retained historic rows would bypass it.

The legacy result should be machine-readable and durable, either a nullable article review marker/status column or a dedicated ledger keyed by article UUID. The likely minimal repository shape is an article field such as `legacyMediaReview` selected/hydrated with the retained post. The migration must be transactional and idempotent: scan retained non-deleted rows, retain raw Markdown, record every offending Markdown image/legacy cover disposition, and clear a legacy external `cover_url` only when `cover_media_id` is already the authoritative cover. Preserve raw `coverUrl` and source text otherwise for an explicit administrator repair. Soft-deleted rows must remain lossless; they should not unexpectedly become public or be destructively rewritten.

Public reading remains defensive even before all legacy records are repaired: the renderer removes a disallowed `src`, so no external request results. A marker must block future publication or update-to-published transitions with an actionable validation field. Do not download/import an external image, rewrite external anchors, replace retained source with a placeholder URL, or silently delete historical Markdown. The public cover projection already ignores `coverUrl`; preserve that separation.

## 05-02 — concrete production collection and mounted-directory pipeline

### Required separation and data flow

```text
rehearsal policy -> createBackupSet -> verifyBackupSet -> generated restore
                                    \-> unchanged rehearsal root/project/cleanup authority

strict production policy -> validate production source authority
  -> concrete collector
       -> PostgreSQL custom dump
       -> unchanged portable export v1
       -> every API-owned source + derivative media byte
       -> sanitized config/image-digest/migration inventory
       -> restrictive staging -> manifest -> COMPLETE -> production verification -> atomic final set
  -> authenticated encryption
  -> concrete already-mounted-directory provider
       -> exclusive incomplete ciphertext -> fsync -> receipt/catalog -> atomic rename
  -> receipt digest equality -> safe retention -> redacted result -> alert-outcome record
```

Phase 5 does not consume a pre-existing rehearsal set. The scheduled production entry creates a fresh complete set under its own source authority, verifies it, and immediately hands that exact final root to the encryption/mounted pipeline. The closest collection analog is `scripts/backup/create.mjs`: restrictive umask, unique incomplete staging, exact payload inventory, manifest and last-written `COMPLETE`, verification, then atomic rename. Reuse its ordering, not its `blogxverify_*` policy, Compose project, path validation, or cleanup authority.

The only shared implementation with rehearsal is non-mutating content inspection. Extract `verifyCompleteBackupSetContents(root, rootValidator)` into `scripts/backup/content-verifier.mjs`; its validator argument is mandatory and runs before any member read. Existing `verifyBackupSet(root)` in `manifest.mjs` keeps its exact signature/result and continues to wrap only `validateFinalBackupRoot`/`validateBackupStaging`. Production wraps the same content verifier only after `validateProductionBackupSource`. The two wrappers must reject one another's roots before reading payload bytes, and `paths.mjs`, rehearsal `policy.mjs`, `create.mjs`, `restore.mjs`, and their cleanup functions remain unchanged.

The production collector exposes a closed named-operation seam—`dumpPostgresCustom`, `writePortableExportV1`, `copyApiMedia`, and `readAllowlistedInventory`—so tests can inspect ordering and inject faults. The shipped implementation owns the fixed executable/entrypoint and exact source roots. Policy must never supply argv, SQL, shell, module, URL, or an arbitrary file list. A successful local proof uses a fresh exact `blogxprodverify_<token>` project/database/media authority plus an exact generated `blog-x-production-source-*` base; it creates and verifies real database/export/media/config-image-migration bytes instead of reusing a fixture set.

The successful transfer path is the concrete `mounted-directory.mjs` filesystem provider operating on an already provisioned mount. It validates a non-link exact mount root and strict identity sentinel, writes only authenticated ciphertext below an exclusive restrictive incomplete sibling, fsyncs file and directories, binds receipt/catalog to ciphertext and source manifest digests, and atomically renames. Local acceptance injects mount inspection for an exact generated directory but executes these real copy/fsync/rename/receipt/catalog/retention/result/alert operations. The fake transport is used only to force short writes, receipt mismatch, unavailable mount, list/catalog failure, retention failure, result failure, and alert failure; `scope: generated-fake` is never successful evidence. Generated mounted/pipeline scopes are executable local evidence but are also never live off-host evidence.

Authenticated encryption binds format/version, set ID, source manifest SHA-256, creation time, retention-policy ID, and destination-profile ID using fresh in-memory data material. Receipt digest equality is a precondition for retention. Retention parses only expected encrypted-set names beneath the exact prefix, validates receipt/catalog integrity, deletes nothing on ambiguity, and preserves the configured minimum known-good objects. Alert confirmation is part of the terminal result; an unconfirmed alert makes the pipeline nonzero.

## 05-03 — versioned release decisions and canonical Phase 5 proof

### Required state machine

```text
tracked canonical evidence: BLOCKED only

temporary pre-release bundle --offline validation--> PRE_RELEASE_READY
                                                    |
                                  explicit authorized human deployment outside repository
                                                    v
                                        DEPLOYMENT_OCCURRED (external fact)
                                                    |
temporary post-release bundle + bound pre-decision -> POST_RELEASE_VERIFIED
                                              \-> failed smoke/rollback -> POST_RELEASE_FAILED / BLOCKED
```

`scripts/release-gate/{schema,validate,bundle}.mjs` supplies the strict existing pattern. Version the document rather than bolting an optional field onto v1: v2 pre-release sections must omit any post-release requirement; post-release evidence must separately bind the pre-release bundle hash/decision ID, deployed artifact digest, actual domain smoke outcome, and continue/rollback decision. Malformed, tampered, stale, future, secret/address-bearing, linked, extra, or mismatched inputs remain `INVALID`; legitimate missing/failed prerequisite facts remain `BLOCKED` (or an explicit non-success post result), never synthetic authorization.

The gate only evaluates local regular files. `scripts/release-gate.mjs` should offer expectation flags for `--expect-blocked`, `--expect-pre-release-ready`, and `--expect-post-release-verified`, but no `deploy`, `transition`, `unfreeze`, or rollback command. A pre-release-ready result is a decision to consider a separately authorized action, not an executable action. The checked-in evidence must remain locator-free and `BLOCKED`; the boundary audit must reject tracked `PRE_RELEASE_READY` and `POST_RELEASE_VERIFIED` exactly as it rejects v1 `READY`.

The pre-release backup artifact must consume the concrete 05-02 result contract: fresh collector proof for database dump, portable export, source/derivative media and config/image/migration inventory; independent restore linkage; authenticated mounted ciphertext and receipt; safe retention; redacted result; and confirmed alert outcome. Scope is decisive: `generated-production-pipeline`, `generated-mounted-fixture`, and `generated-fake` always block pre-release readiness. Only future live collect-then-mounted evidence can satisfy the production section, and that live evidence is absent in Phase 5.
