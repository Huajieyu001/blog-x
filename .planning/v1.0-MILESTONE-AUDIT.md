# Blog X v1.0 Milestone Audit

**Audited:** 2026-08-09T13:37:20Z

**Status:** gaps_found

**Safety state:** production release remains `BLOCKED`

## Executive Summary

All four phases and all 21 implementation plans are complete, and every phase-level verification report passed. The milestone-level audit nevertheless found three cross-phase contradictions that were not visible when each phase was judged in isolation:

1. Earlier Markdown behavior permits external image requests while the final topology requires all browser media requests to remain on the blog origin.
2. The local atomic backup and isolated restore implementation is verified, but there is no executable production daily/off-host/encrypted backup path.
3. The release validator requires post-release evidence before returning the READY decision needed to authorize that release.

These gaps reduce milestone requirement coverage to 22/25 and block v1.0 closeout. They do not weaken the current freeze: the canonical release state remains locator-free `BLOCKED`, and the audit did not contact either cloud server.

## Critical Gaps

### G1 — Published external images violate OPS-01

`apps/api/src/content/markdown.ts` accepts both `/media/<uuid>` and every absolute `http:`/`https:` image. `apps/api/test/markdown-renderer.test.ts` and `apps/web/e2e/phase1-publishing.spec.ts` explicitly preserve an external image, and no CSP limits `img-src` to the blog origin. A published page can therefore trigger third-party or mixed-content browser media requests despite the formal same-origin requirement.

**Affected requirement:** OPS-01.

**Closure:** Restrict published image sources to root-relative `/media/<uuid>` authority, migrate/reject legacy external cover and Markdown image values, add known-bad external/mixed-content tests, and retain ordinary external hyperlinks separately.

### G2 — Production daily/off-host backup is not executable

The backup format, atomic completion, tamper detection and isolated restore rehearsal are strong. However, `validateBackupRoot` only accepts generated temporary `blog-x-backup-verify-*` roots, `parseBackupPolicy` only accepts `blogxverify_*` Compose/database authority, and `create.mjs` never consumes off-host destination, encryption, retention, or alert references beyond syntax validation. The tracked systemd service calls this verifier-only path and cannot establish the production daily backup promised by OPS-03.

**Affected requirements:** OPS-03 and OPS-05.

**Closure:** Add a separate fail-closed production backup adapter with explicit safe destination allowlisting, encrypted off-host transfer, retention and alert-result evidence; keep generated local rehearsal paths isolated; then exercise the service/timer against an authorized non-production recovery target before any production release evidence can pass.

### G3 — READY requires evidence that only exists after release

The schema makes `postRelease` a mandatory READY section. Its artifact requires a recorded rollback decision and at least three smoke checks, while the runbook correctly says those checks happen after the actual HTTPS release. One state therefore cannot grant pre-release GO without already possessing post-release results.

**Affected requirement:** OPS-05.

**Closure:** Split the state machine into `PRE_RELEASE_READY` and `POST_RELEASE_VERIFIED`. Deployment remains a separate explicitly authorized human action; the second gate records smoke/continue/rollback results afterward and must never retroactively authorize the first.

## Non-Critical Technical Debt

- Legacy `TracerAdmin.tsx` and direct `POST /articles/publish` remain present. The route is guarded but bypasses the normal article service/lifecycle surface.
- The canonical Phase 4 full gate does not directly rerun every Phase 1 lifecycle browser spec; it relies partly on database regressions and later browser journeys.
- `apps/web/app/admin/taxonomy/page.tsx` casts upstream JSON rather than parsing the shared strict contract.
- Future READY evidence is byte-hashed but not signed and is not directly bound to the complete backup-set and restore-report digests.
- Planning metadata still has a Phase 3 update footer in REQUIREMENTS.md, while AGENTS.md stack/architecture/conventions remain placeholders.

## Safety Conclusion

- The canonical evidence remains `BLOCKED` with unresolved authorization, host baselines, private link/same-origin, daily/off-host backup, retention, RPO/RTO, TLS/renewal, rollback and post-release facts.
- Compose exposes only the local Web loopback port; API and PostgreSQL remain private to the Compose network.
- The release validator has no SSH, SCP, rsync, HTTP client, child-process deployment, or host mutation adapter.
- Neither cloud server was contacted or modified during this audit.

## Recommended Gap-Closure Sequence

Create one focused closure phase with three ordered plans:

1. Enforce same-origin published media and close legacy external-image paths.
2. Separate local rehearsal from a safe production backup adapter and produce daily/off-host/encryption/retention evidence contracts.
3. Split pre-release readiness from post-release verification, then rerun the complete Phase 1-4 acceptance and milestone integration audit.

The milestone must not be archived or tagged until all three gaps are closed and this audit returns `passed`.
